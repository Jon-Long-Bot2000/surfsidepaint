# Surfside proposal workflow

Version 1.0.0 retains the approved 1693-Poli PDF and webpage design. It creates a
separate project source folder, a PDF, a static webpage, and a Before/After gallery
for every address. Existing proposals are never regenerated by a new project.

## Start from a new Codex chat

Open a new chat in the same local Codex project and say:

> Create a proposal for 123 Oak Street, Ventura, CA.

The project instructions route that request to this workflow. Codex creates a
feature branch from the latest `origin/main`, preserves unrelated changes, creates
the local project folder, gathers missing intake details and photos, and produces
a local preview. Publication requires your approval. A new chat does not need the
history of the Poli conversation.

The parent repository is `~/Projects/surfsidepaint`. The installed workflow is
`_proposal-workflow/`; project source folders are `_proposal-projects/<slug>/`.
The current `1693 Poli/` folder can remain the Codex project launch folder: its
instructions point to the shared workflow. New proposal files go into sibling
project folders in the parent repository, not inside the Poli job.

## Commands

Use the Codex bundled Python interpreter (ReportLab, Pillow and pypdf are already
available). Poppler's `pdftoppm` must be on PATH. HEIC/HEIF images additionally
require `heif-convert`; JPEG, PNG and WebP need no extra image converter.

```sh
python3 _proposal-workflow/proposal.py new "123 Oak Street, Ventura, CA" --slug 123-Oak
```

`new` creates only local inputs; branch creation is performed by Codex following
`WORKFLOW.md`. It refuses to reuse an existing project or website route. Each
project includes a complete `_template/` snapshot. Use that snapshot for every
later command so future template updates do not alter existing proposals:

```sh
python3 _proposal-projects/123-Oak/_template/proposal.py intake _proposal-projects/123-Oak
python3 _proposal-projects/123-Oak/_template/proposal.py build _proposal-projects/123-Oak
python3 _proposal-projects/123-Oak/_template/proposal.py serve _proposal-projects/123-Oak --port 4174
```

Edit `proposal-details.json` and place photographs under `assets/before/` and
`assets/after/`. Copy a hero photo into `assets/` and set `web.hero_image` to its
relative path. Its `web.hero_caption` is optional and must be specific to that
image. No Zillow caption or Poli photograph is inherited. `photos` is an optional
list of `{path, caption}` records to append selected photographs to the PDF;
gallery photos are not automatically appended to the PDF.

Use plain text in summaries, scope and terms; the site address is bolded in the
PDF automatically. Codex refines the task list into an ordered `scope_paragraph`.
`tasks` also supports explicit `{title, description}` items when requested.
`schedule` is rendered beneath the first pricing row. `materials` is rendered in
the Materials row (created automatically if needed). These appear in addition to
the rows' descriptions. Avoid duplicating the same wording in both places.
An amount of zero is a real price, while null is pending. A pricing row with
`amount_label: ""` has no dollar amount (for materials billed separately).

Draft builds carry a visible draft notice and cannot be staged. Once intake,
pricing and terms are confirmed, create and review a final build:

```sh
python3 _proposal-projects/123-Oak/_template/proposal.py build _proposal-projects/123-Oak --final
python3 _proposal-projects/123-Oak/_template/proposal.py check _proposal-projects/123-Oak
```

Outputs are `output/site/` (only publishable files), `output/pdf-pages/` (all PDF
page PNGs for visual review), and `output/build.json` (validation and file hashes).
The stable download filename is `<slug>_Surfside_Proposal.pdf`. The proposal preview
opens the PDF on tap; the separate CTA downloads it. The preview server prints
desktop and available LAN addresses and serves only the generated site folder.

After the user approves publication:

```sh
python3 _proposal-projects/123-Oak/_template/proposal.py stage _proposal-projects/123-Oak --repo .
```

Staging refuses incomplete, stale, modified or draft builds. An existing URL can
be replaced only by the same project ID. Case-insensitive collisions and paths
outside the destination are rejected. The command stages files to the route but
does not run `git add`, commit, merge or push; Codex performs and verifies those
steps under the publication approval. The final URL is
`https://surfsidepaint.com/123-Oak/`.

## Source and publication boundaries

- `_proposal-projects/` is ignored by Git. Draft data, original photos, local
  previews and template snapshots stay local; back up that folder with your normal
  computer backup. The public repository retains approved PDFs and optimized photos.
- `_proposal-workflow/` begins with an underscore so the current GitHub Pages
  Jekyll build excludes its tools and source templates. Do not add it to Jekyll's
  `include` list or introduce `.nojekyll` without reviewing that boundary.
- Staging copies only the generated static site. No JSON contractor intake,
  original HEICs, temporary files, backend or R2 configuration is included.
- Generated pages are public, with `noindex, nofollow` as a search preference;
  this is not access control. Never imply they are private or password protected.
- No Worker, R2 bucket, paid service, browser upload or recurring automation is
  needed or enabled by this workflow.
- Bump `VERSION` when changing the template. Existing projects retain their own
  snapshot and public output until explicitly revised and approved.

## Validation

```sh
python3 -m unittest discover -s _proposal-workflow/tests -v
```

The tests exercise independent projects, escaped content, real PDF/image output,
draft publication blocks, stale/tampered outputs, route collisions and isolated
updates. Test fixtures are synthetic; no customer examples are bundled.

On macOS the PDF uses the same Arial fonts as the approved reference. On another
OS it uses ReportLab's bundled Vera fonts; visually review before using that
fallback for a production proposal.
